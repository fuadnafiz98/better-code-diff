# Batch dependency bumps

Collapse N dependency-bump PRs into one PR whose lockfile is resolved once, in the environment production builds with. Each bot PR resolves its lock in isolation against a stale base, so merging them one at a time produces N conflicting locks; regenerating once produces the tree that will actually ship.

Never close or comment on any PR until the replacement branch exists, builds, and is pushed.

## Read the incoming PRs

1. Take PR numbers or URLs from the request. If the user asked for a whole backlog instead, list candidates (`gh pr list --author app/dependabot --json number,title,files`) and confirm the set with them before touching anything.
2. For each PR record: package, from-version, to-version, and which files it touches.
3. Classify each bump by whether the PR changes the manifest:
   - **Direct** — the PR edits `package.json` (or `pyproject.toml`, `go.mod`, `Cargo.toml`). Read the exact replacement string from `gh pr diff <n>`; do not reconstruct the range specifier yourself.
   - **Transitive** — the PR touches the lockfile only. The package sits under another dependency's range. Confirm this by finding who depends on it in the lockfile, and name that parent in the write-up.
4. Note which ecosystem and which lockfile each PR belongs to. Split the work per lockfile; one rollup branch may still carry several, but each lockfile is regenerated by its own tool.

## Prepare the branch

1. Confirm the working tree is clean and the base branch matches its remote. Stop if either is false.
2. Branch from the base with the name the user asked for, or `deps/rollup-<YYYY-MM-DD>` when they did not name one.
3. Apply each direct bump to the manifest with an **asserted** edit: fail loudly if the old string is absent or not unique. A silent no-op here yields a lockfile that looks regenerated but is not.

## Regenerate the lockfile once

1. Look for a repo-owned lock script before reaching for a bare install — check `scripts/`, the manifest's script block, `Makefile`, and CI workflows for something that pins the build image or toolchain version. Use it, or reuse its pinned image and flags. Local toolchains resolve platform-specific optional dependencies differently from CI, and that difference reaches production.
2. Run the install so it honors the manifest edits: `npm install` (or `pnpm install` / `yarn install` / `bun install`) with audit and funding output off.
3. Transitive bumps need a second, explicit step. An install alone keeps whatever the lockfile already pins, because the locked version still satisfies the range. Name those packages: `npm update <pkg>...`, `pnpm update <pkg>...`, `yarn up <pkg>`.
4. Do not hand-edit a lockfile. If a target version will not resolve, report the conflicting constraint instead.

## Audit the lockfile diff semantically

Line counts prove nothing about a lockfile. Compare resolved versions between the base lockfile and the new one, and enumerate every entry that was added, removed, or changed.

1. Confirm each requested target version landed.
2. Account for every other change. A transitive bump legitimately drags its own dependencies along — list them. Anything you cannot attribute to a requested bump is a finding: report it and stop rather than folding an unexplained upgrade into a routine rollup.
3. Check for removals and additions separately from version changes. A dropped platform-specific optional dependency means the lock was generated on the wrong platform.

## Verify

Run the repo's own checks, not a substitute for them: lint, tests, and a production build. A dependency bump changes runtime and build behavior, so the build matters most and a green test suite does not stand in for it.

Establish a baseline for anything already failing on the base branch — pre-existing failures are not evidence against the rollup, but only if you have actually checked. Report new failures against the specific bump that caused them.

## Commit, open, supersede

1. Commit with the roll-up listed line by line: package, version transition, and the PR number it replaces. Say which environment produced the lockfile.
2. Open the PR. Include a table of the bumps and their superseded PR numbers, the extra transitive changes with the parent that pulled them, the exact commands that regenerated the lock, and the verification results with the baseline noted.
3. `Closes #N` does not close a pull request — GitHub only auto-closes issues. Close each superseded PR explicitly.
4. Comment on each before closing it, naming the replacement PR and why it supersedes this one. A bare close leaves the bot's PR looking rejected and tells reviewers nothing. This closing note is the one PR comment the flow owns; it does not license posting reviews or verdicts on PRs.
5. If the rollup is later rejected, the originals reopen — say so rather than deleting their branches.

## Report

State the resulting PR, every bump it carries with its superseded number, unattributed lockfile changes if any survived review, verification results against baseline, and which originals are now closed.
